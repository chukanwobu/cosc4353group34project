2. Database Technology Justification & Architecture

Selected Engine: Relational Database (SQLite / RDBMS)

Our team selected an RDBMS (SQLite) with enforced foreign key constraints (PRAGMA foreign_keys = ON;) based on the following evaluation:

  • Relational Integrity: Services, active queues, student queue entries, and user credentials share strict relational lifecycles. Foreign keys prevent orphaned records and maintain referential integrity.
  • ACID Transaction Compliance: Queue transitions (serving next, reordering, cancelling) require atomic write safety to eliminate race conditions under concurrent requests.
  • Database-Level Validations: Native CHECK and UNIQUE constraints enforce domain boundaries (100-character service name limits, 200-character notes limit, valid status/priority enums) directly in the database engine.
  • Zero-Friction Grading Portability: SQLite embeds natively in Node.js without requiring external server installations, cloud credentials, or docker configuration. TAs can clone and run the project immediately.

3. Database Schema Design (3 points)

-- Enable foreign key constraint enforcement in SQLite
PRAGMA foreign_keys = ON;

-- 1. UserCredentials Table (Encrypted Authentication)
CREATE TABLE IF NOT EXISTS UserCredentials (
    user_id TEXT PRIMARY KEY,
    email TEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,
    role TEXT NOT NULL CHECK(role IN ('user', 'admin')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 2. UserProfile Table (User Details)
CREATE TABLE IF NOT EXISTS UserProfile (
    profile_id TEXT PRIMARY KEY,
    user_id TEXT UNIQUE NOT NULL,
    full_name TEXT NOT NULL,
    email TEXT NOT NULL,
    student_id TEXT,
    phone TEXT,
    preferences TEXT DEFAULT '{}',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES UserCredentials(user_id) ON DELETE CASCADE,
    FOREIGN KEY (email) REFERENCES UserCredentials(email) ON UPDATE CASCADE
);

-- 3. Service Table (Organizational Services)
CREATE TABLE IF NOT EXISTS Service (
    service_id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT UNIQUE NOT NULL CHECK(length(name) <= 100),
    description TEXT NOT NULL,
    duration INTEGER NOT NULL CHECK(duration > 0),
    priority TEXT NOT NULL CHECK(priority IN ('low', 'medium', 'high')),
    is_open BOOLEAN NOT NULL DEFAULT 1,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 4. Queue Table (Active Service Queues)
CREATE TABLE IF NOT EXISTS Queue (
    queue_id TEXT PRIMARY KEY,
    service_id INTEGER NOT NULL,
    status TEXT NOT NULL CHECK(status IN ('open', 'closed')),
    created_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (service_id) REFERENCES Service(service_id) ON DELETE CASCADE
);

-- 5. QueueEntry Table (Waiting Students & Order)
CREATE TABLE IF NOT EXISTS QueueEntry (
    entry_id TEXT PRIMARY KEY,
    queue_id TEXT NOT NULL,
    service_id INTEGER NOT NULL,
    user_id TEXT,
    user_name TEXT NOT NULL,
    student_id TEXT NOT NULL,
    notes TEXT CHECK(length(notes) <= 200),
    position INTEGER NOT NULL,
    join_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    priority TEXT NOT NULL CHECK(priority IN ('low', 'medium', 'high')),
    status TEXT NOT NULL CHECK(status IN ('waiting', 'served', 'canceled')),
    estimated_wait INTEGER NOT NULL DEFAULT 0,
    FOREIGN KEY (queue_id) REFERENCES Queue(queue_id) ON DELETE CASCADE,
    FOREIGN KEY (service_id) REFERENCES Service(service_id) ON DELETE CASCADE,
    FOREIGN KEY (user_id) REFERENCES UserCredentials(user_id) ON DELETE SET NULL
);

-- 6. NotificationHistory Table (Audit Log & Notifications)
CREATE TABLE IF NOT EXISTS NotificationHistory (
    notification_id TEXT PRIMARY KEY,
    user_id TEXT,
    ticket_id TEXT,
    service_name TEXT NOT NULL,
    message TEXT NOT NULL,
    type TEXT NOT NULL CHECK(type IN ('info', 'success', 'warning', 'alert')),
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status TEXT NOT NULL CHECK(status IN ('sent', 'viewed')),
    FOREIGN KEY (user_id) REFERENCES UserCredentials(user_id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_queue_entry_status ON QueueEntry(queue_id, status, position);
CREATE INDEX IF NOT EXISTS idx_notification_user ON NotificationHistory(user_id);

4. Security & Data Integrity Validations

1. Password Encryption (bcrypt): Plain-text passwords are never stored. Passwords are salted and hashed with bcrypt (cost factor 10) on registration and verified via bcrypt.compare() on login.

2. Database Constraints: Mandatory uniqueness on emails, max-length constraints (100 characters on service names, 200 characters on visit notes), and enumerated domain checks on priority and status.
